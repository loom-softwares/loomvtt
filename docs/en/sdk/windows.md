# Window Manager (`window-manager.ts`)

Window system (draggable, focusable).

```typescript
import { windowManager, WindowLike } from '../core/window-manager.js';
```

## API

```typescript
windowManager.open<P>(id: string, WindowClass, props?: P): Promise<void>
windowManager.focus(id: string): void
windowManager.close(id: string): void
windowManager.closeAll(): void
windowManager.get(id: string): WindowLike | undefined
windowManager.rerenderIfOpen(id: string): void
windowManager.mountExisting(id: string, instance: WindowLike): Promise<void>
windowManager.closeTopmost(): boolean
```

- `get(id)`: returns the open window instance, or `undefined` if not open.
- `rerenderIfOpen(id)`: re-renders the window body if open; no-op otherwise.
- `mountExisting(id, instance)`: registers a window instance already created externally (idempotent — no-op if `id` is already open).
- `closeTopmost()`: closes the window with the highest z-index; returns `false` if none are open.

## WindowLike

```typescript
interface WindowLike {
  setZ(z: number): void;
  mount(): void | Promise<void>;
  destroy(): void | Promise<void>;
}

## BaseWindowOptions

When extending `BaseWindow`, you can provide options in `super()` to control window behavior:

```typescript
interface BaseWindowOptions {
  id: string;
  title: string;
  icon?: string;
  width?: number;
  height?: number | 'auto'; // 'auto' calculates based on scrollHeight (max-height 90vh)
  documentId?: string;
  submitOnChange?: boolean; // Rule 5: auto-save debounce
  showFooter?: boolean; // If false, hides the default footer with save/cancel buttons
  anchorTop?: boolean; // If true, anchors the window to the top of the screen instead of centering
  allowOverflow?: boolean; // If true, doesn't clip content bleeding outside the window rect (overflow:hidden becomes visible)
  overflowMargin?: number; // Only with allowOverflow:true — px of content hanging outside (e.g. floating side tab). Disappears from screen without this.
}
```

### `allowOverflow` / `overflowMargin` — content leaking outside the window

By default every window clips (`overflow: hidden`) anything that goes beyond its own
rectangle. If your sheet has a floating element outside the border (bookmark-style side
tab, suspended modifier popup — common pattern in previous version sheets),
enable both together:

```typescript
super({
  ...
  allowOverflow: true,
  overflowMargin: 70, // actual width of the leak (e.g. 58px rail + padding)
});
```

`allowOverflow` alone only turns off the visual clipping — the window can still be dragged
to any position, and if the leak falls outside the browser VIEWPORT (not the
window), it disappears with no error. `overflowMargin` solves this: it adds to the margin that
`constrainToViewport()` uses to lock dragging, so the window can never get
close enough to the screen edge for this content to leave the visible area.

This alone doesn't clip ancestral CSS with `overflow-y: auto` — `.loom-window-body`
has this by default (body scroll), and `overflow-y` implies non-visible `overflow-x`
even without declaring it. If the floating element is a child of `.loom-window-body`, your system's
CSS needs to free this up too, scoped by its own class (passed in
`classes: [...]` in the window options — becomes a class of the root `.loom-window`):

```css
.my-system-sheet .loom-window-body {
  overflow: visible;
}
```

## BaseWindow

All windows extend `BaseWindow` (`src/windows/base-window.ts`) or `LoomDocumentSheet` (`src/windows/document-sheet.ts`).

Windows with a form use `LoomFormData` (`src/core/form-data.ts`) to serialize body fields into a typed object, with required validation:

```typescript
import { LoomFormData } from '../core/form-data.js';

const fd = new LoomFormData(bodyElement);
if (fd.missing.length > 0) { /* show required field toast */ }
const data = fd.toObject();
```

### ApplicationV2 Parity

`BaseWindow` implements parity with the ApplicationV2 API:
- `renderChild(instance)` / `renderChild(id, class, options)`: Renders a sub-window and automatically attaches it to the `this.childIds` array. The parent window's lifecycle closes the child windows.
- `activateListeners(html)`: compatibility stub with the original platform's V1 `Application` — called on every `mount()`/`rerenderBody()` with the window's root element. Converted V1 systems that override this method continue working without adaptation.

### Compatibility classes on window chrome

The root element and the header generated by `mount()` receive extra classes, besides the native Loom ones, to match CSS selectors written for the origin platform:

| Element | Native Loom Classes | Added Alias |
|---|---|---|
| Window root | `loom-window app window-app` | `application` |
| Header | `loom-window-header` | `window-header` |
| Title | `loom-window-title` | `window-title` |
| Control button | `loom-window-control-btn` | `header-control` |
| Close button | `loom-window-close` | `header-control` |
| Resize handle | (internal) | `window-resize-handle` |

Title and header use real `<h1>`/`<header>` tags (they used to be `<div>`) — converted system CSS depending on a tag selector (`h1 { ... }`) now matches.
- On `LoomDocumentSheet`, the `_toggleDisabled(state: boolean)` method is available to enable or disable interactions on the entire form (e.g. during async save).
- On `LoomCategoryBrowser`, the `_prepareCategoryData()` method (abstract) can be inherited and, by default, throws an implementation error (native interface behavior).

## Tabs

`LoomHandlebarsMixin` (`application.ts`) implements `changeTab(tab, group)`, parity
with the original `ApplicationV2.changeTab()` — toggles the `active` class in nav and
content by attribute, not by separate template. Minimal markup:

```html
<nav class="loom-window-tabs">
  <a data-tab="general" data-group="primary" class="active">General</a>
  <a data-tab="details" data-group="primary">Details</a>
</nav>

<div class="tab" data-tab="general" data-group="primary">...</div>
<div class="tab" data-tab="details" data-group="primary">...</div>
```

- Nav: any element with `[data-tab][data-group]` — click is already captured by
  delegation (no `data-action` needed, nor custom listener).
- Content: `<div class="tab" data-tab="..." data-group="...">` — the `.tab` class
  (not `.tab-content`, which is something else unrelated in `components.css`) is what
  the mixin toggles.
- `tabGroups: Record<string, string>` stores the active tab per group — set the
  initial tab by setting `this.tabGroups['primary'] = 'general'` before the first render (or
  leave empty: the first tab marked `active` in HTML counts as initial state).
- Ready CSS in `client/styles/windows.css` (`.loom-window-tabs` / `.loom-window
  .tab[data-group]`) — don't write `display:none`/`.active` by hand, it already exists.

## LoomDialog (DialogV2 Parity)

The `LoomDialog` class (exported in the SDK) replaces old custom dialogs, providing strict parity with `DialogV2`.

```typescript
import { LoomDialog } from '/_loom/sdk/index.js';

// Static Methods (create and await the Modal's response)
const result1 = await LoomDialog.prompt({ window: { title: "Prompt" }, content: "..." });
const result2 = await LoomDialog.confirm({ window: { title: "Confirm" }, content: "..." });
const result3 = await LoomDialog.input({ window: { title: "Input" }, content: "..." });
const result4 = await LoomDialog.wait({ window: { title: "Wait" }, content: "..." });

// Instance
const dialog = new LoomDialog({ window: { title: "My Dialog" }, content: "..." });
dialog.render();
dialog.resolve("Final value"); // Resolves the dialog's promise remotely and closes
```

### `LoomDialog.query(user, type, config)`

Allows dispatching a dialog modal to a specific session user.

> **Phase 1/Phase 2 Note:** Currently, the method checks if the requested `user` is the current client (comparing `session.userId`). If local (Phase 1), it displays the interface on screen. If the target is a remote client (Phase 2), the action is currently **pending** and returns `null` with a warning log (awaits WebSocket round-trip to be implemented).

## Example

```typescript
import { MyWindow } from '../windows/my-window.js';

await windowManager.open('my-window', MyWindow, { data: {} });
windowManager.focus('my-window');
windowManager.close('my-window');
```

If a window with the same ID is already open, `open` focuses it instead of creating another.
